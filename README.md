## Repository Structure Explanation

The NextWatch project follows a professional machine learning pipeline structure that separates concerns across multiple layers, ensuring maintainability, reproducibility, and scalability.

**Data Directory** serves as the foundation for all data processing workflows. The `raw/` subdirectory stores the original, unmodified datasets and sample inputs for testing. This separation prevents accidental modification of source data during development. The `processed/` subdirectory contains all intermediate and final data products generated by preprocessing and feature engineering stages, maintaining a clear lineage of data transformations that can be audited and reproduced.

**Models Directory** persists trained machine learning artifacts in an isolated location outside the source code. This separation ensures that model files—binary serialized objects—are not versioned alongside code, reducing repository bloat while maintaining reproducibility. Each trained model is accompanied by its associated artifacts (scalers, encoders) to ensure consistent feature transformation during inference.

**Source Code Module** (`src/`) organizes all production-ready Python code with clear responsibility boundaries. Each module serves a single, well-defined purpose in the ML pipeline, from data ingestion through prediction. The `config.py` module acts as a centralized configuration hub, eliminating hardcoded paths and enabling environment-specific customization without code changes.

**Supporting Directories** (`notebooks/`, `reports/`, `logs/`) provide spaces for exploratory work, generated artifacts, and debugging information respectively. These directories remain independent from the core ML pipeline, allowing experimentation without affecting production code. Empty directories are tracked using `.gitkeep` files, ensuring they exist in cloned repositories.

**CLI Entry Point** (`main.py`) provides the primary interface for executing the ML pipeline. It orchestrates the data flow through preprocessing, feature engineering, training, and prediction stages, exposing a command-line interface that abstracts the complexity of module interactions.

## Data Flow Mapping

The NextWatch system implements a sequential, unidirectional data pipeline that moves information from raw input through increasingly refined representations:

**Input Stage**: Raw data enters the system as CSV files in `data/raw/`. The `sample_predictions.csv` file contains test examples matching the input format of production data, enabling validation of the prediction pipeline without requiring actual trained models.

**Preprocessing Stage**: The `data_preprocessing.py` module reads raw data and applies cleaning operations—missing value imputation, duplicate removal, and range validation—producing `data/processed/processed_movies.csv`. This stage ensures data quality and consistency before feature engineering.

**Feature Engineering Stage**: The `feature_engineering.py` module transforms cleaned data into ML-ready features. It performs categorical encoding (converting genre labels to numeric codes), numeric feature scaling (standardizing ranges), and interaction feature creation (e.g., rating × popularity). Fitted transformers (StandardScaler, LabelEncoder) are serialized to `models/feature_scaler.pkl` and `models/label_encoder.pkl` for consistent application during inference.

**Data Splitting Stage**: The `train.py` module splits the engineered features into training (80%) and testing (20%) sets, stratified by target variable distribution. These splits are saved to `data/processed/train_data.csv` and `data/processed/test_data.csv`, enabling reproducible model evaluation and debugging.

**Model Training Stage**: The training pipeline uses the preprocessed training set to fit either a K-Nearest Neighbors or Random Forest regression model. Cross-validation (5-fold) assesses generalization performance across data subsets. The trained model is serialized to `models/movie_recommendation_model.pkl`.

**Evaluation Stage**: The `evaluate.py` module generates comprehensive performance metrics (R², RMSE, MAE) using the held-out test set. Residual analysis identifies systematic prediction errors. Evaluation reports are printed to console and optionally saved to `reports/`.

**Prediction Stage**: During inference, new movie data enters through the `predict.py` module. Features are prepared using the same preprocessing pipeline, transformed using the fitted scalers and encoders loaded from `models/`, and passed to the trained model. Predictions include confidence scores derived from nearest-neighbor distances (KNN) or feature importance variance (Random Forest).

**Batch Prediction Pipeline**: The CLI's batch mode reads multiple samples from a CSV file, applies the full prediction pipeline to each record, and returns aggregated results in tabular format, enabling bulk recommendation generation.

## Design Justification

**Separation of Raw and Processed Data**: This structure prevents accidental corruption of source data during development. Raw data in `data/raw/` serves as a versioned reference point, while `data/processed/` contains all derived artifacts. This enables data scientists to revert to original values if preprocessing errors are discovered, and to compare multiple preprocessing approaches without re-downloading source data.

**Isolated Models Directory**: Machine learning model files are large binary objects that should not be version-controlled alongside code. By storing them in a dedicated `models/` directory, the main codebase remains lightweight, enabling faster cloning and reducing Git repository bloat. Model artifacts (scalers, encoders) are collocated with the main model, establishing a clear dependency relationship.

**Function-Based Source Code Architecture**: The `src/` modules contain pure functions rather than classes or top-level execution code. This design enables:
- **Composable Pipelines**: Functions can be chained in different orders for experimentation.
- **Independent Testing**: Each function can be tested in isolation without side effects.
- **Clear Reproducibility**: Function outputs depend only on inputs and configuration, enabling bit-for-bit reproducible results when using fixed seeds.

**Centralized Configuration Module**: `config.py` contains all paths, hyperparameters, and magical constants. This eliminates scattered hardcoded values across modules and enables:
- **Environment-Specific Setup**: Different paths for local, testing, and production environments.
- **Easy Hyperparameter Tuning**: Model settings can be adjusted in a single location.
- **No Circular Dependencies**: All modules import from `config`, creating a star dependency graph rather than circular imports.

**Independent Pipeline Stages**: Training and prediction pipelines are completely independent, with no shared mutable state. This design enables:
- **Offline Model Training**: Train once, deploy many times.
- **Safe Inference**: Predictions cannot modify the training dataset.
- **Parallel Development**: Analysts can optimize training while engineers optimize prediction serving.

**Dedicated Exploration and Reporting Directories**: `notebooks/`, `reports/`, and `logs/` are physically separated from production code. Notebooks can safely contain exploratory analysis without affecting the reproducible pipeline. Reports contain generated artifacts (plots, metrics summaries) that document model behavior. Logs provide debugging information for troubleshooting failures.

**Path Management Through Configuration**: All file operations reference paths defined in `config.py` using `Path` objects (pathlib). This approach ensures:
- **Cross-Platform Compatibility**: Paths work identically on Linux, macOS, and Windows.
- **Single Source of Truth**: Changing a data path requires modifying only one location.
- **Clear Dependencies**: Code clearly declares which data and model artifacts it requires.

## Architecture Overview

### Module Responsibilities

1. **config.py**: Central configuration hub
   - All constants and paths
   - Feature definitions
   - Model hyperparameters
   - Data validation ranges

2. **data_preprocessing.py**: Data cleaning and preparation
   - Load raw CSV data
   - Handle missing values
   - Remove duplicates
   - Validate numeric ranges
   - Standardize column names

3. **feature_engineering.py**: Feature creation and transformation
   - Encode categorical features (genre → numeric)
   - Create interaction features (rating × popularity)
   - Scale numeric features (StandardScaler/MinMaxScaler)
   - Select and transform features for modeling

4. **train.py**: Model training and persistence
   - Split data into train/test
   - Train KNN or Random Forest models
   - Perform cross-validation
   - Save trained models to disk

5. **evaluate.py**: Performance assessment
   - Calculate regression metrics (RMSE, MAE, R²)
   - Generate residual statistics
   - Create evaluation reports
   - Save results to JSON

6. **predict.py**: Inference and recommendations
   - Validate user input
   - Prepare features for prediction
   - Make recommendations
   - Support batch predictions

### Key Design Principles

- **No Circular Imports**: Each module imports only from `config` and standard libraries
- **Independent Pipelines**: Training and prediction can run independently
- **Function-Based**: All executable code is in functions, no top-level execution
- **Reproducibility**: Seeds and random states are configurable
- **Type Hints**: All functions include type annotations
- **Logging**: Comprehensive logging throughout

- **Solution**: Ensure Python is installed and added to PATH. Try `python3` instead of `python`.

- **Solution**: Ensure virtual environment is activated (look for `(venv)` in prompt). Run `pip install -r requirements.txt` again.


- **Training Time**: 1-5 seconds (depending on dataset size)
- **Prediction Time**: <10ms per prediction
- **Model Size**: ~2-5 MB (pickled)

- **matplotlib**: Visualization (optional)
